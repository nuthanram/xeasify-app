## 2026-10-09 — Pin path_provider_foundation to unblock `flutter run` on Windows
- What changed: `pubspec.yaml` adds `dependency_overrides: path_provider_foundation: 2.5.1` (transitive dep of `google_fonts` → `path_provider`).
- Why: `path_provider_foundation` 2.6.0 moved to a native-assets hook that needs `package:objective_c`. Compiling that hook runs `dart compile kernel` with the Flutter SDK's own `dart.exe` path unquoted, which breaks for every target (not just macOS/iOS, web included) whenever the SDK or project path contains a space — our dev machine's SDK lives under `...\Bhargav projects\flutter`. A directory junction to a space-free path doesn't help, since Windows resolves the junction back to the real path when the executable actually runs. 2.5.1 is the last release before the native-assets hook was introduced, so it has no `objective_c` dependency and the build (web, confirmed via `tool/run_web_dev.ps1`) succeeds again. Revert this override once the SDK is reinstalled to a space-free path or upstream fixes the path-quoting bug.

## 2026-10-09 — Cap Gradle daemon memory at 2 GB
- What changed: `android/gradle.properties` `org.gradle.jvmargs` lowered from Flutter's template default `-Xmx8G -XX:MaxMetaspaceSize=4G -XX:ReservedCodeCacheSize=512m` to `-Xmx2G -XX:MaxMetaspaceSize=1G -XX:ReservedCodeCacheSize=256m`. `flutter build apk --debug` still succeeds.
- Why: the development machine has 7.8 GB of RAM. An 8 GB heap let one Gradle daemon (started by `flutter run`/`build` or by VS Code's Java extensions) fill all memory, and leftover daemons stayed resident for hours. Locally, `.vscode/settings.json` (git-ignored) also stops the VS Code Java/Gradle extensions from importing `android/` as a Java project.

## 2026-10-09 — Creator step 3: email code and SMS code (Firebase Phone Auth)
- What changed: `verify_contact_screen.dart` rewritten for OTPs. **Email:** SEND CODE → `POST /accounts/creator/verify-email/initiate/`, then a 6-digit field → `POST /accounts/creator/verify-email/` (`AccountsRepository.confirmEmailCode`); shows wrong-code / expired / rate-limit messages from the backend, a resend countdown from `resend_after` / `retry_after`, and CHANGE EMAIL. **Mobile number:** new `lib/services/phone_otp.dart` — Firebase Auth sends the SMS (`signInWithPhoneNumber` with Firebase's invisible reCAPTCHA on the web, `verifyPhoneNumber` on Android, incl. auto-read), the code is checked by Firebase, the Firebase ID token goes to `POST /accounts/creator/verify-phone/` (`AccountsRepository.verifyPhone`), and the Firebase session is signed out at once. Numbers are normalised to E.164 (a bare 10-digit number gets +91); Firebase error codes become plain messages; 60 s resend countdown. Firebase is initialised in code from new build settings `FIREBASE_API_KEY`, `FIREBASE_APP_ID`, `FIREBASE_PROJECT_ID`, `FIREBASE_MESSAGING_SENDER_ID`, `FIREBASE_AUTH_DOMAIN` (`lib/core/config.dart`, `config/dev.example.json`); without them the phone section says it is not set up. When the backend reports `verified` the screen returns to the marketplace. New dependency `firebase_auth` ^5.3.0 (pub moved `firebase_core` 3.15.2 → 3.15.0 and `firebase_messaging` 15.2.10 → 15.2.8 to fit). Tests: `accounts_repository_test.dart` (4), new `phone_otp_test.dart` (5); 28 pass, `flutter analyze` no new issues, `flutter build web` and `flutter build apk --debug` succeed. README: step-3 setup.
- Why: phone + email OTP is the MVP onboarding. Firebase Phone Auth is the only free SMS option (10 SMS/day free on the Blaze plan, free test numbers, Google handles India's DLT rules); the backend already verifies Firebase phone tokens. Backend side (same day, `xeasify-core`): email codes instead of links, `FIREBASE_PROJECT_ID`, and `verify-phone` answers 400 instead of 401 so a failed phone sign-in no longer signs the creator out of the app.
- Needs before it works on dev: a Firebase project with Phone sign-in enabled (Blaze for real SMS, or test numbers) and its web app's values in `config/dev.json`; the backend env secret's `FIREBASE_PROJECT_ID` and Brevo SMTP settings.

## 2026-10-09 — Creator onboarding step 3: email verification screen

It reads `GET /accounts/me/` (email / phone verified flags, sign-in email to prefill), sends the link with `AccountsRepository.startEmailVerification()` (`POST /accounts/creator/verify-email/initiate/`), and I'VE OPENED THE LINK rereads `/me`; once the backend says `verified` it goes to the marketplace. The phone section says phone verification is not in the app yet. At `metrics_granted` the marketplace banner's button is VERIFY EMAIL & PHONE and opens this screen. The marketplace now re-syncs `signup_state` from `/accounts/me/` each time it opens (creators only), so the banner follows changes made elsewhere (email link, admin) without signing in again. New `test/accounts_repository_test.dart` (2 tests); 21 pass, `flutter analyze` shows no new issues, `flutter build web` succeeds.
- Why: step 3 had no screen, so a creator could never finish onboarding from the app, and the banner kept showing a stale step after admin changes.
- Not done: phone verification. The backend only accepts a Firebase Phone Auth ID token, so it needs a Firebase project with phone sign-in, Firebase web config in the app and `FIREBASE_CREDENTIALS_PATH` on the backend. Until then a creator reaches `verified` only through admin. On dev the email is sent with whatever `EMAIL_BACKEND` the env sets; with the console backend the link is only in the `api` / `worker` logs.

## 2026-10-09 — Make the "grant metrics access" onboarding step actionable
- What changed: `AccountsRepository.grantMetricsAccess()` (`POST /accounts/creator/grant-metrics/`). The marketplace's onboarding banner (`_OnboardingBanner`) is now a `StatefulWidget`: at `signup_state == social_linked` it shows a GRANT METRICS ACCESS button that calls it and, on success, syncs `signup_state` into `authProvider` so the banner updates immediately; failures (e.g. the stored token lacks the metrics scope) show the backend's error inline. Step 3 (phone + email verification) is unchanged — still informational only.
- Why: YouTube web sign-in already requests the metrics scopes during Google consent, but the backend only advances past `social_linked` when `/accounts/creator/grant-metrics/` is explicitly called, and nothing in the app called it — every creator was stuck on "STEP 2 OF 3" with no way to proceed. Found while manually testing the YouTube sign-in flow against dev.
- Not done: phone/email verification (step 3) still has no screen. Phone verification needs Firebase Phone Auth wired up for web (not configured here — see README known issues); doing email verification alone can't reach `verified` since the backend requires both.
## 2026-10-09 — Instagram / Facebook creator sign-in through Meta's SDK

New `test/meta_sign_in_test.dart` (7 tests); 19 pass, `flutter analyze` shows no new issues, `flutter build web` and `flutter build apk --debug` succeed (the APK carries the configured ids). README: creator sign-in options, `config/dev.json`, testing from another machine.

- Needs before it works: a Meta app (App ID, client token in `config/dev.json`; app id + secret as `META_APP_ID` / `META_APP_SECRET` in the backend's dev secret), testers added while the app is in development mode, and the Android debug key hash registered.

## 2026-10-04 — Ask for location permission once on marketplace
- What changed: `LocationService` gained `needsPrompt()`/`markPrompted()` (a one-time flag in `shared_preferences`); `MarketplaceScreen` shows an explanatory dialog on first open and requests the OS location permission only if the user taps Allow.
- Why: `requestPermission()` existed but was never called, so GPS check-in could never run. Location stays optional: declining is remembered, the user is not asked again, and the app works without it.

## 2026-10-04 — Add Android permissions to main manifest
- What changed: `android/app/src/main/AndroidManifest.xml` now declares `INTERNET`, `ACCESS_COARSE_LOCATION`, `ACCESS_FINE_LOCATION` and `POST_NOTIFICATIONS`; `.gitignore` ignores `android/.kotlin/`; the Flutter-generated `android/` project, `test/`, `.metadata` and `analysis_options.yaml` are now tracked.
- Why: `INTERNET` was only declared in the debug/profile manifests, so release builds could not reach the API. Location and notification permissions are optional at runtime (the app works if the user denies them) but must be declared to be requested.
